## Опис реалізації `RetryPolicy`
Реалізовано власний узагальнений клас `RetryPolicy`, який інкапсулює патерн повторних спроб з експоненційною затримкою та випадковим відхиленням (**jitter**):
- **Поля та конструктор:** `_maxRetries` (`int`), `_initialDelay` (`TimeSpan`), `_jitterFactor` (`double`, за замовчуванням `0.2`).
- **Формула розрахунку затримки:**
  $$\text{delay} = \text{initialDelay} \times 2^{\text{retryAttempt}} \times \left(1 + \text{random.NextDouble()} \times \text{jitterFactor} \times 2 - \text{jitterFactor}\right)$$
- **Узагальнений метод `Execute<T>(Func<T> operation, Func<Exception, bool>? shouldRetry = null)`:** виконує довільну функцію `Func<T>`, логує кожну спробу, причину збою та тривалість паузи перед наступним повтором, а також підтримує фільтрацію винятків через делегат `shouldRetry`.

### Продемонстровані сценарії в `Main`
1. **Успішне відновлення після тимчасового збою:** перші два виклики `FetchRemoteConfig()` генерують `HttpRequestException`, політика виконує експоненційні паузи (~300 мс, ~600 мс із jitter), і на 3-й спробі операція повертає конфігурацію.
2. **Вичерпання ліміту спроб (`maxRetries = 3`):** метод `AlwaysFailingService()` стабільно викидає `IOException`; після 1 основної та 3 повторних спроб політика прокидає останній виняток у `Main`.
3. **Миттєва відмова для невідновлюваних помилок:** коли `ArgumentException` не відповідає умові `shouldRetry`, повторні спроби не виконуються.

Висновок щодо меж застосування патерну Retry з Exponential BackoffПатерн Retry з Exponential Backoff та Jitter є ефективним інструментом для подолання короткочасних (транзитивних) мережевих або інфраструктурних збоїв, оскільки поступово знижує навантаження на проблемний сервіс і розносить повторні запити клієнтів у часі. Водночас цей патерн має чіткі межі застосування: його не можна використовувати для помилок бізнес-логіки чи валідації (які ніколи не виправляться при повторі), для тривалих збоїв без поєднання з Circuit Breaker (інакше потоки застосунку будуть надовго заблоковані очікуванням), а також для неідемпотентних операцій без захисту від дублювання.

Відповіді на контрольні запитання
Чому експоненційна затримка зазвичай ефективніша за фіксовану для тимчасових збоїв?
При перевантаженні сервера або бази даних фіксовані короткі паузи продовжують створювати постійний тиск на систему. Експоненційне збільшення інтервалу ($t, 2t, 4t, 8t\dots$) дає серверу дедалі більше часу на розвантаження черг та відновлення працездатності.

Для чого потрібен jitter і як він зменшує ризик одночасних повторних спроб?Якщо тисячі клієнтів отримали помилку одночасно, без jitter усі вони зроблять повторну спробу в ту саму мілісекунду (ефект Thundering Herd — «громового стада»). Випадкове відхилення (jitter) рівномірно розподіляє повторні запити в часовому вікні, згладжуючи піки навантаження.

Яку роль відіграє делегат shouldRetry у власній реалізації політики повторних спроб?Він дозволяє відокремити тимчасові винятки, які варто повторювати (HttpRequestException, TimeoutException), від критичних помилок конфігурації, авторизації чи валідації (ArgumentException, UnauthorizedAccessException), для яких повторні спроби не мають сенсу.

У яких випадках повторна спроба не є безпечною та її слід заборонити?Коли операція не є ідемпотентною (наприклад, списання коштів із рахунку, відправка email-повідомлення або створення нового запису без унікального ключа запиту), а також коли перевищено загальний SLA-таймаут користувацького запиту.
