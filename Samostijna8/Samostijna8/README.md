## Опис реалізації
- **`Cache<TKey, TValue>`**: узагальнений клас кешу з обмеженою ємністю (`_capacity`) та політикою витіснення найстаріших елементів **FIFO (First In, First Out)**.
- Для швидкого доступу за ключем ($O(1)$) використовується `Dictionary<TKey, TValue>`, а для відстеження порядку додавання ключів — черга `Queue<TKey>`.
- При переповненні кешу найстаріший ключ витягується через `_keysOrder.Dequeue()` та видаляється зі словника.
- У проєкті **`Samostijna8.Tests`** на базі фреймворку **xUnit** реалізовано 7 юніт-тестів для перевірки додавання, отримання, оновлення існуючого ключа, підрахунку `Count`, перевірки `ContainsKey`, обробки винятку `KeyNotFoundException` та витіснення елементів при перевищенні ємності.

Чому для реалізації політики FIFO зручно поєднувати Dictionary<TKey, TValue> з Queue<TKey> або LinkedList<TKey>?Словник (Dictionary) забезпечує миттєвий пошук значення за ключем зі складністю $O(1)$, але не гарантує порядок вставки при видаленні, тоді як черга (Queue) зберігає точну хронологічну послідовність додавання ключів за принципом «перший прийшов — перший вийшов».

У яких випадках метод Get повинен викидати KeyNotFoundException, а коли доцільніше використовувати підхід на кшталт TryGetValue?Метод Get викидає KeyNotFoundException, коли очікується, що ключ обов'язково існує, а його відсутність є помилкою логіки. Підхід TryGetValue (який повертає bool) доцільніший, коли відсутність елемента в кеші (cache miss) є звичайним, очікуваним робочим сценарієм.

Які тести є критично важливими для перевірки політики витіснення елементів з кешу?Тест на додавання кількості елементів, що перевищує _capacity (перевірка, що видалено саме найперший доданий елемент, а новіші залишилися), тест на збереження незмінного Count == _capacity після витіснення, а також тест на оновлення значення вже існуючого ключа без зайвого видалення елементів.
