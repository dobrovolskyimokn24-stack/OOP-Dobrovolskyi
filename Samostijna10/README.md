## Опис реалізованих методів `CollectionUtils`
- **`Map<TSource, TResult>`**: приймає `Func<TSource, TResult>` та проєктує кожен елемент вхідної колекції у новий тип.
- **`MaxBy<T, TKey>`**: приймає `Func<T, TKey>` (де `TKey : IComparable<TKey>`) та знаходить елемент із найбільшим значенням обраного ключа.
- **`Filter<T>`**: приймає `Predicate<T>` та відбирає елементи, які задовольняють задану умову.
- **`ForEach<T>`**: приймає `Action<T>` та виконує задану дію для кожного елемента колекції.

---

## Аналіз та порівняння з LINQ

### 1. Чому делегати корисні для створення таких утиліт?
Делегати дозволяють відокремити алгоритм обходу колекції від конкретної бізнес-логіки обробки елемента. Завдяки цьому один узагальнений метод (наприклад, `Filter<T>` або `Map<TSource, TResult>`) може працювати з будь-якими типами даних і різними правилами без дублювання циклів `foreach`.

### 2. Як лямбда-вирази спрощують виклик цих методів?
Лямбда-вирази (`p => p.Price > 1000m`) дозволяють передавати компактну анонімну функцію безпосередньо в місці виклику методу замість створення окремих іменованих методів або громіздких анонімних делегатів. Компілятор автоматично виводить типи параметрів на основі узагальненої колекції.

### 3. Порівняння власних утиліт із вбудованими операторами LINQ

| Метод `CollectionUtils` | Аналог у LINQ | Відмінності в роботі та виконанні |
| :--- | :--- | :--- |
| `Map<TSource, TResult>` | `Enumerable.Select` | Власний `Map` виконується **негайно** (створює `List<TResult>`), тоді як LINQ `Select` використовує **відкладене виконання** (deferred execution через `yield return`). |
| `Filter<T>` | `Enumerable.Where` | Власний `Filter` приймає `Predicate<T>` і одразу матеріалізує список, а LINQ `Where` приймає `Func<T, bool>` і обчислюється при ітерації. |
| `MaxBy<T, TKey>` | `Enumerable.MaxBy` (.NET 6+) | Обидва виконуються негайно за один прохід $O(n)$, але в LINQ додатково підтримується передача кастомного `IComparer<TKey>`. |
| `ForEach<T>` | `List<T>.ForEach` | У стандартному LINQ немає `ForEach` для `IEnumerable<T>` (є лише у `List<T>`), оскільки концепція LINQ базується на чистих функціях без побічних ефектів. |

Чому делегати є зручним механізмом для передавання поведінки в узагальнені методи?
Вони забезпечують типобезпечне посилання на метод із визначеною сигнатурою, дозволяючи параметризувати не лише типи даних (<T>), а й саму логіку їх обробки.

У чому різниця між Func<T, TResult>, Action<T> та Predicate<T>?
Func<T, TResult> приймає аргумент типу T і повертає результат типу TResult; Action<T> виконує дію над T і нічого не повертає (void); Predicate<T> є спеціалізованим делегатом, який приймає T і завжди повертає bool.

Які переваги дає поєднання generic-методів і лямбда-виразів під час роботи з колекціями?
Код стає лаконічним, декларативним, легко читається, повністю зберігає перевірку типів на етапі компіляції та виключає дублювання циклів обробки.

У яких випадках власні утиліти на кшталт Map чи Filter корисно реалізувати самостійно, навіть якщо існує LINQ?
Коли потрібна специфічна бізнес-логіка (наприклад, вбудоване логування, обробка помилок під час ітерації, гарантована негайна матеріалізація без алокацій ітераторів) або в обмежених середовищах без повної бібліотеки System.Linq.
